### 2.3 ★ 对共享工具 `build.ps1` 的一处**追加式**修改（必须知悉）

`Patches\PerScopeMeshSurgerySettings.cs` 用 `Newtonsoft.Json`（`JsonConvert.DeserializeObject/SerializeObject`；加固后这两个调用位于第 436 / 440 行的两个包装器内）。
4.0.13 的 `.csproj` 是靠 NuGet 包引用的；本机这套 BepInEx 安装的 `BepInEx\core\` 下**没有** `Newtonsoft.Json.dll`，

- 原脚本写法：`foreach ($n in @('BepInEx.dll','0Harmony.dll','Newtonsoft.Json.dll')) { $p = Join-Path $core $n; if (Test-Path $p) {...} }`
  —— 找不到就**静默跳过**，于是第一轮编译报 `CS0246 未能找到类型或命名空间名"Newtonsoft"`。
- 本次修改（`D:\Work area\212\_build\build.ps1` 第 36–45 行）：把 `Newtonsoft.Json` 从那个循环里拿出来，先试 `BepInEx\core\`，**找不到就回落到游戏 `Managed\`**：

```powershell
$newtonsoft = Join-Path $core 'Newtonsoft.Json.dll'
if (-not (Test-Path $newtonsoft)) { $newtonsoft = Join-Path $managed 'Newtonsoft.Json.dll' }
if (Test-Path $newtonsoft) { $refs.Add($newtonsoft) }
```

- **风险**：低。这是纯追加引用；对其它工程（`HideoutNvgFix`、`BetterThermalNightVision`）只是多一个用不到的程序集引用，
  不会改变它们的行为。唯一需要注意的是：若将来某个工程在该目录下放了**另一个** `Newtonsoft.Json.dll`，
  引用的就是游戏 `Managed\` 那份（版本 13.x，随客户端走）。
- **备选方案**（本次未采用）：改 `PerScopeMeshSurgerySettings.cs` 自己写 JSON 序列化，避免这个依赖。
  代价约 150 行手写解析，且会与原版配置文件的格式兼容性产生新风险，因此没有走这条路。

### 2.6 ★ `Newtonsoft.Json` 依赖分析（运行时必需性结论）

> 这是被专门问到的一个问题，因为「插件引用了运行环境里可能解析不到的程序集」正是会造成
> 「插件类型加载失败 / 被静默丢弃」那类故障的形态。结论与依据如下。

**（1）哪个文件、哪个类型的哪两个方法依赖它**

全树检索 `JsonConvert` / `Newtonsoft` / `Formatting.`，**命中点只有 3 处，全在同一个文件里**：

- `Patches\PerScopeMeshSurgerySettings.cs:1` —— `using Newtonsoft.Json;`（**编译期 only**，不产生任何程序集引用）
- `Patches\PerScopeMeshSurgerySettings.cs:436` —— `JsonConvert.DeserializeObject<ScopeMeshSurgerySettingsFile>(json)`（在 `DeserializeJson` 包装器内；
  由 `private static void EnsureLoaded()`（`PerScopeMeshSurgerySettings.cs:341-380`）在第 364 行经该包装器调用）
- `Patches\PerScopeMeshSurgerySettings.cs:440` —— `JsonConvert.SerializeObject(file, Formatting.Indented)`（在 `SerializeJson` 包装器内；
  由 `private static void WriteToDisk()`（`:382-402`）在第 392 行经该包装器调用）

依赖的类型：`Newtonsoft.Json.JsonConvert` 与 `Newtonsoft.Json.Formatting`。
涉及的自有类型：`PiPDisabler.PerScopeMeshSurgerySettings`（静态类），数据模型 `ScopeMeshSurgerySettingsEntry` /
`ScopeMeshSurgerySettingsFile`（**不依赖** Newtonsoft，只是被序列化的 POCO）。

**（2）运行时必需吗？——是「运行时必需」，但只在两条冷路径上，且已有 try/catch**

- `EnsureLoaded()` 是**必需的**：它被 `GetActiveOverride()`（`:181`）、`SaveCustomSettingsForScope()`（`:202`）、
  `SaveActiveScopeVisualSettings()`（`:256`）、`DeleteCustomSettingsForScope()`（`:271`）调用，
  而这四个又被打包在 `MeshSurgeryManager`（`:320-386`、`:742-753`、`:1226`）、`ReticleRenderer`（`:699-1007`）、
  `ScopeEffectsRenderer`（`:531-533`）、`VisualRecoilCompensationPatch`（`:61`、`:168`）、
  `WeaponScalingPatch`（`:72`）调用的 `GetPlane*` / `GetVignette*` / `GetMeshReticle*` / `GetVisualRecoilCompensation`
  等取值器里 —— 也就是说**进战局开镜后每帧都会被走到**。
  但 `EnsureLoaded()` 开头就是 `if (_loaded) return;` 且 `_loaded = true` 写在 try 之前（`:337-340`），
  所以 `JsonConvert` 实际上**一个会话只被解析一次**（首次取值时）。
- `WriteToDisk()` 只在「保存/删除自定义网格手术配置」与「切镜时保存视觉参数」时触发（`:247`、`:262`、`:283`）。
- 两者内部**都已有 try/catch**（`:341-355` / `:360-368`），失败时分别退回默认值 / 只打一条 `[CustomMeshSettings]` 日志。

判据链：

1. **`Assembly-CSharp.dll` 自己就引用 `Newtonsoft.Json, Version=13.0.0.0, PKT=30ad4fe6b2a6aeed`。**
   这意味着游戏本体代码在跑到相关路径时会去加载它；Mono 解析程序集引用的探测路径包括**发起请求的那个程序集所在目录**，

2. **版本与公钥令牌逐字一致**：我们的 `AssemblyRef` 是 `13.0.0.0 / 30ad4fe6b2a6aeed`，
   `Managed\Newtonsoft.Json.dll` 的 `AssemblyName` 也是 `13.0.0.0 / 30ad4fe6b2a6aeed` ——
   **不存在版本绑定失败的情况**（这正是「忘了改版本号导致 FileNotFoundException」的常见成因，本次不适用）。
3. **SPT 自己的 4 个客户端插件也引用它**（`spt-common` / `spt-custom` / `spt-debugging` / `spt-singleplayer`），
   说明在这套安装里该程序集是**被反复加载的常态依赖**，不是边缘条件。→ **结论：运行时可解析，且几乎肯定在我们之前就已经被加载进程。**

**（4）结论**

- **是运行时必需**（不是纯编译期）：`PerScopeMeshSurgerySettings.EnsureLoaded()` / `WriteToDisk()` 会真的调用 `JsonConvert`；
  这两条路径在进战局开镜后必然被走到（首次）。
- **但解析风险判定为「无」**：依据是 `Assembly-CSharp.dll` 自身引用它、版本+PKT 与本产物逐字一致、
  目标文件就在 `Managed\`、且 4 个 SPT 插件也引用它。
- **失败形态也不会是「插件被静默丢弃」**：与 `BepInPlugin` 版本号那个坑不同，程序集解析失败**不会**让 BepInEx 在扫描阶段
  丢弃插件类型（BepInEx 扫描只看特性与类型元数据，不需要解析方法体里的程序集引用）。
  最坏情况是运行期抛 `FileNotFoundException` / `TypeLoadException`。

**（5）已实施的加固：Json bridge（`[MethodImpl(NoInlining)]` 边界）**

> 说明：这条**不是修 bug，是防御性改动**——（4）的三条判据成立时，它在实践中不改变任何东西。
> 之所以仍然做，是因为**后果不对称**：万一真的解析失败，旧写法的表现是
> `MeshSurgeryManager` / `ReticleRenderer` **每帧抛异常**，而这恰好会伪装成「移植失败 / 画面坏掉」，
> 污染实机诊断数据；把它降级为「一条警告 + 用内置默认值继续跑」的代价只有十几行。

**问题**：CLR/Mono 对方法体里的程序集引用，是在**该方法被 JIT 编译时**解析的。
旧写法把 `JsonConvert` 直接写在 `EnsureLoaded()` / `WriteToDisk()` 体内，于是：

- 解析失败时，异常会在**调用这两个方法的地方**抛出（因为 JIT 是在调用点触发的），
  写在 `EnsureLoaded()` **方法内部**的 try/catch **未必接得住**；
- 而 `EnsureLoaded()` 又被打包在 `GetPlane*` / `GetVignette*` / `GetMeshReticle*` 等取值器里，
  进战局开镜后**每帧**都会走到 ⇒ 每帧一次异常风暴。

**做法**（`Patches\PerScopeMeshSurgerySettings.cs`，文件内注释标题为 "Json bridge"）：

1. 把两个 `JsonConvert` 调用各自挪进一个**只做这一件事**的小方法，并标 `[MethodImpl(MethodImplOptions.NoInlining)]`：

   ```csharp
   [MethodImpl(MethodImplOptions.NoInlining)]
   private static ScopeMeshSurgerySettingsFile DeserializeJson(string json)
       => JsonConvert.DeserializeObject<ScopeMeshSurgerySettingsFile>(json);

   [MethodImpl(MethodImplOptions.NoInlining)]
   private static string SerializeJson(ScopeMeshSurgerySettingsFile file)
       => JsonConvert.SerializeObject(file, Formatting.Indented);
   ```

   `NoInlining` 是关键：它阻止把这两个包装器的方法体内联进调用方，从而把**程序集解析失败推迟到「调用这两个包装器的那一刻」**，
   而调用点在 `Try` 块里。

2. 调用处用 try/catch **包住对包装器的调用**，只在该层拦截「后端不可用」这一类异常：

   ```csharp
   try { parsed = DeserializeJson(json); }
   catch (Exception jsonBackendEx) when (IsJsonBackendFailure(jsonBackendEx))
   {
       OnJsonBackendUnavailable("load", jsonBackendEx);
       return;
   }
   ```

3. 「后端不可用」由异常**类型**判定（`IsJsonBackendFailure`）：
   `FileNotFoundException` / `FileLoadException` / `TypeLoadException` / `TypeInitializationException` /
   `MissingMethodException` / `MissingFieldException` / `BadImageFormatException` / `SecurityException`。
   **普通 JSON 解析错误与 IO 错误（`JsonException` / `IOException` / `UnauthorizedAccessException`）不在其中**，
   它们照旧落到原来的外层 catch，**行为与不加加固时完全相同**。

4. 失败后置 `_jsonBackendUnavailable = true`，之后**所有 JSON 路径直接跳过**（不再重试、不再抛），
   `PerScopeMeshSurgerySettings` 于是退化为**内置默认值**继续工作；
   并且**只发一条 Warning**（`PiPDisablerPlugin.LogSource.LogWarning`）。

**关于这条 Warning 为什么不受 `Debug logging` 控制**：`Debug logging` 默认是关的，而「自定义按瞄具参数已失效」
是玩家/测试者**必须能看见**的状态（否则会把它误判成画面 bug）。因此它刻意走**无条件 Warning**，
且被一次性标志锁住——**整个会话最多一条**，不存在刷屏。

**「解析成功时行为零差异」的具体含义**（本次要求的硬约束，逐条对应）：

- 同样的重载、同样的实参、同样的异常传播路径：包装器是**表达式体转发**，没有参数变换、没有类型转换、没有吞异常；
- 包装器**只在** `parsed = ...` / `json = ...` 赋值处被调用，`File.ReadAllText` / `File.WriteAllText` / `File.Exists` 的
  调用顺序与位置**逐行未动**；
- `IsJsonBackendFailure` 为 false 时异常过滤器**不拦截**，异常沿原路径抛给原来的 `catch (Exception ex)`，
  连日志文案 `[CustomMeshSettings] Failed to load settings json: ...` 都一字未改；
- `_jsonBackendUnavailable` 在后端可用时**永远是 false**，那两处 `if (_jsonBackendUnavailable) return;` 是**死分支**，
  `EnsureLoaded()` 的 `_loaded` 单次语义、`WriteToDisk()` 的调用时机均不变；
- `NoInlining` 只影响 JIT 时机，**不影响语义**；两个包装器是 `private static`，不进入任何对外 API。

**这一点是可自动验证的，且已固化进核对脚本**：脚本新增
`Newtonsoft.Json containment: N method(s) reference it, M of them lack NoInlining (expect 2 / 0)`，
用 Cecil 枚举**全程序集每一个方法体**，断言「引用 Newtonsoft 的方法恰好只有那两个包装器，且都带 NoInlining」。
当前产物实测：

```
=== Newtonsoft.Json containment: 2 method(s) reference it, 0 of them lack NoInlining (expect 2 / 0) ===
  PiPDisabler.PerScopeMeshSurgerySettings::DeserializeJson   ImplAttrs=NoInlining
  PiPDisabler.PerScopeMeshSurgerySettings::SerializeJson     ImplAttrs=NoInlining
```

也就是说：`EnsureLoaded` / `WriteToDisk`（以及其它任何方法）的 IL 里**都不含** Newtonsoft 引用 ⇒ 它们的 JIT 不会因缺程序集而失败 ⇒
「降级而不是每帧抛异常」这条保证**由脚本守住，不会随以后改代码悄悄回退**。
若哪天有人把 `JsonConvert` 挪回普通方法体，脚本会直接打出 `!! FAIL: a Newtonsoft.Json reference leaked outside a NoInlining wrapper`。

## 6. ★ 猜测 / 简化 / stub 清单（逐条写明风险）

> 这一节是本次移植**最需要阅读**的部分。以下每一处都不是「能编译就没事」，而是**有具体行为假设**的。

### 6.1 【功能降级 / 空操作】`OpticComponentUpdaterLateUpdate_DisablePiP` 的 transpiler 在 4.1.5 不生效

- 位置：`Patches\PiPDisabler.cs:414-432`。
- 模组原意：把 `OpticComponentUpdater.LateUpdate()` 里的 `Camera.Render()` 换成自己的 `MaybeRender()`，
  从而**彻底不让那张画中画相机出图**。
- **4.1.5 事实（本次用 IL 反汇编确证，不是推断）**：`OpticComponentUpdater.LateUpdate()`（`_decomp_full:869135`，方法体到 869205）
  **体内没有任何 `Camera.Render()` 调用**。把它的全部 `call*` 指令列出来，与渲染相关的只有
  `Camera.set_useOcclusionCulling`、`Camera.set_fieldOfView`、`Behaviour.set_enabled`、若干后处理组件的同步赋值。
  IL 直接比对 `Camera::Render` 的调用方：整个 `Assembly-CSharp.dll` 里只有 **7 处**（截图 / 深度相机 / 雪景 / 影棚等），
  **没有一处与光学相机相关**。
- 结论：该 transpiler 的匹配条件（`callvirt Camera::Render`）**永不命中**，Transpiler 原样返回所有指令 ——
  **它是空操作，不会报错，也不会崩**。`MaybeRender()` 成为死代码。
- **缓解**：PiP 相机的渲染控制**并没有丢**，由同一文件的另外两条路径覆盖：
  - `OpticComponentUpdaterLateUpdate_DisablePiP.Prefix`（`PiPDisabler.cs:382-401`）→ `ForceDisable(cam)`
    （`PiPDisabler.cs:317-344`：`cam.enabled = false`、`cam.targetTexture = null`、`cam.cullingMask = 0`）；
  - `PiPDisabler.TickBaseOpticCamera()`（`PiPDisabler.cs:64-90`）每帧对缓存到的全部光学相机重放 `ForceDisable`。
  - 另外 `VanillaOpticSuppressionPatches.ReleaseRenderTexture()` 还会主动 `Destroy` 那张 `_renderTexture`
    并把全局 `_CamTex` 置空。
- **风险等级**：低（有等价机制），但**属于「原版行为没有 100% 复刻」**，如实登记。MVP 的实机验证（第二轮）证明
  压制链路在缺这条 transpiler 的情况下仍然生效（日志出现 `Skipped vanilla optic manager enable`）。
- **后续可选处置**：① 删掉这段死代码；② 改为在 `Prefix` 里直接 `cam.enabled = false`（其实已经是这么做的）。
  本次**保留原样**，理由是：无副作用，且万一将来客户端又在 `LateUpdate` 里恢复显式 `Camera.Render()`，它会自动重新生效。

### 6.2 【推断】`method_23` → `OnAimOrPoseChanged`，`Single_2` → `HeadBobbing`

- 两条都是「高置信度推断」，**不是字节码级确证**。原因是本机**没有 4.0.13 的 `Assembly-CSharp.dll`**，
  无法做「旧字节码 → 新字节码」的交叉比对；SPT 每个版本重新生成反混淆映射，`method_23` 这个编号在新版里已不存在。
- 推断依据（详见 4.3-8、4.3-14）：PWA 类内全量检索无 `method_23`；4 个写 FOV 的候选里只有 `OnAimOrPoseChanged`
  是「姿态/瞄准变化时重算基础 FOV」；`HeadBobbing` 是 PWA 内唯一读「游戏 FOV 设置值」的成员；
  `-15f` 常数与 `HeadBobbing - 15f` / `CameraManager.AimDeltaFov = 15f` 三处互相印证。
- **可静态确认的部分**：`OnAimOrPoseChanged` 内**确实**有一条 `callvirt CameraManager::SetFov`
  （IL 核对 FOUND），transpiler 一定能替换到 —— 所以「替换会不会落空」这件事是确定的；**不确定的是「这个函数是不是当年那个 method_23」**。
- **风险与后果**：
  - 若映射正确 → FOV 覆盖/变焦手感与原版一致。
  - 若映射错误 → transpiler 会替换掉**别处**的 FOV 写入：症状是「站姿切换/瞄准时 FOV 行为异常」，
    极端情况是开镜 FOV 抖动。**不会崩游戏**（Harmony 会捕获补丁异常）。
- **实机验证方法（已落地为代码，不需要再改代码）**：`PWAMethod23Patch.Prefix` 里已内置命中日志，
  实机只要把 `Debug logging` 打开，然后**在游戏里切站姿（站/蹲/趴）与开/关镜**，
  日志里出现 `[PWAMethod23] hit #...` 即为**确认这条映射成立**。日志样例（一行）：

  ```
  [PWAMethod23] hit #1: target='OnAimOrPoseChanged' (4.0.13 obfuscated PWA pose/aim FOV writer — see porting doc 4.3-14) caller='ProceduralWeaponAnimation.set_IsAiming' camFov=52.35 baseFov=65.00 aiming=True sprint=False optic=True frame=123456
  ```

  - `target=` 是 Harmony 注入的 `__originalMethod.Name`，即**我们实际挂在哪个方法上**（权威值，不是硬编码字符串）；
  - `caller=` 是**谁触发了它**（`IsAiming` setter / `UpdateCameraFovForced` / 姿态变化等），
    这一项才真正回答「姿态变化会不会走到这里」；
  - `camFov` / `baseFov` / `aiming` / `sprint` / `optic` 给出当时的上下文，便于判断是否在开镜状态。
  - **判读**：切站姿/开关镜能看到命中 ⇒ 映射成立；若切站姿**完全不出现**而只有别的事件（如切枪）出现 ⇒ 映射存疑。
- **日志的成本控制（三条硬约束，已在代码里落实，见 `PWAMethod23Patch.cs:29-115`）**：
  1. **受 `Settings.DebugLogging` 控制**（默认 **false**）——关闭时在方法最开头 `return`，连字符串都不构造；
  2. **节流：同一秒最多一条，且同帧绝不重复**（`frame == _lastLogFrame || second == _lastLogSecond` 直接跳过），
     切站姿时不会刷屏；
  3. **全程 try/catch**（含 `GetCallerName()` 的 `StackTrace`）——诊断代码绝不能影响这条每帧热路径上的 FOV 覆写。
  其中 `GetCallerName()` 的栈回溯**只在真的要写日志那一刻才执行**（每秒最多 1 次），不在热路径上。
- **回退方式**：`Patcher.cs` 里注释掉 `SafeEnable<PWAMethod23Patch>();` 一行即可（FOV 改由 `FovController` 的
  其它路径 + `Settings.BaselineFOV` 承担）。**注意**：这条验证日志不需要回退机制——它默认就是关的。

### 6.3 【推断】`method_3` → `CalculateAfterRecoilWeaponOffset`，`AfterRecoilDefaultPosition` → `_afterRecoilDefaultPosition`

- 依据比 6.2 硬：`_afterRecoilDefaultPosition` 在 `NewRotationRecoilProcess` 内**只有两个写入点**，
  其中一个是 `Reset()` 的整体复位；「把随机回落偏移清零」这件事**只有挂在 `CalculateAfterRecoilWeaponOffset` 上才成立**。
- 残留不确定性：无法排除 4.0.13 的 `method_3` 其实是**调用链上游**的 `CalculateRecoil()`（757168）或
  `CalculateReturnTrajectory()`（757231）。若是那样，挂在下游只影响「同一帧内更晚被覆盖」的时序，效果差别很小。
- 该 patch 受 `Settings.ForceRecoilReturnToZero` 控制（`Settings.cs:274`，**默认 true**），属可选观感功能，与「禁用画中画」主链无关。
- **风险等级**：低。

### 6.4 【简化 / 收窄】`RestoreLodWhileInInventory` 的目标从 `Player` 改挂 `Player.FirearmController`

- 原语义：玩家**任何形式的「背包打开」**都触发 `CameraSettingsManager.RestoreIfPending()`（恢复 LOD 偏置）。
- 4.1.5 现实：`SetInventoryOpened(bool)` 在 `EFT.Player` 上**不存在**；它由 `IHandsController` / `IItemRelatedView`
  声明，并在**几十个**操作类与控制器上各自实现（元数据里 60+ 个声明/实现点，包括一批操作类如
  `EmptyHandsOperation` 560616、`DropBackpackOperation` 560556 等）。没有任何一个「共同基类」能一网打尽。
- 本次做法：挂 `EFT.Player/FirearmController::SetInventoryOpened(System.Boolean)`（**唯一存在的实现，元数据已确认**）。
- **覆盖面差异（已知并接受）**：只在「手里拿着枪」时开背包才会触发恢复。
  空手 / 手持物品 / 特殊控制器路径**不触发**。
  - 为什么这个收窄可以接受：`CameraSettingsManager.RestoreIfPending()` 只有在「刚看过倍镜、且把
    `KeepScopedLodBiasUntilInventory` 设为 true」时才有实际效果（该开关 **默认 false**，`Settings.cs:247`），
    而那个场景**必然手里拿着枪**。
  - 另一个兜底：`CameraSettingsManager.Restore()` 在退出倍镜时也会走一遍（除非开着 `KeepScopedLodBiasUntilInventory`），
    `PiPDisablerPlugin.OnModEnabledChanged` / `OnDestroy` 也会 `ForceRestore()`。
- **风险等级**：低（功能面收窄，不会误触发、不会崩）。
- **替代方案（未采用）**：① 对每个 hands controller 逐个注册 patch（脆弱、数量随版本变）；
  ② 挂 `IHandsController` 接口方法（IL 里接口方法无方法体，Harmony 打不上）。

   - **风险**：若 4.1.5 的瞄具 prefab 改了命名/层级，裁切平面会取不到，表现为「镜身挡视野」或
     「网格没被裁切」。日志线索：`[ScopeHierarchy] FindScopeRoot FAILED`、`[ScopeHierarchy][DEBUG] TryGetPlane: ALL fallbacks failed`。
   - 这个 JSON 是 **75,536 字节**的按瞄具路径录制的数据，**无法静态确认是否仍匹配**。
2. **准星重绘（ReticleRenderer）与镜外效果（ScopeEffectsRenderer）**
   - 依赖 `CameraEvent.AfterForwardAlpha` 的 CommandBuffer、stencil 分层、viewport 计算、`SSAA.GetOutputWidth()` 等。
   - **风险**：最容易出现「编译通过但画面不对（准星偏位/大小不对/镜外模糊位置错）」。
   - 两个 shader bundle 的 **UnityFS 头是 `2022.3.43f1`**，与客户端 Unity 版本逐字一致 ⇒ 序列化格式兼容；
     但 bundle 内**编译好的 shader 变体针对哪个平台/图形 API 无法从文件头断定**（见 6.8）。
3. **`LensTransparency`**：MVP 已实机验证（缺它高倍镜全黑，加上后恢复），且文件**逐字节未改**，风险最低。

### 6.8 【无法静态验证】shader bundle 的变体兼容性

- `pipdisabler_reticle_shaders.bundle`（7,709 字节）与 `pipdisabler_effect_shaders.bundle`（8,117 字节）
  头部均为 `UnityFS 5.x.x 2022.3.43f1`，与目标客户端 `UnityPlayer.dll` 的 `2022.3.43f1 (85497d293fa1)` 一致。
- **未知项**：bundle 内部的 shader 变体是针对哪个平台（Windows/Mac/Linux）与哪个图形 API（D3D11/D3D12/Vulkan）编的。
  若与实机不符，`LoadAllAssets<Shader>()` 能取到 Shader 对象但可能没有可用变体（材质显示为洋红/失效）。

  （模组是按 `Shader.name` 字符串查找的，见 `ReticleRenderer.cs:1123`、`ScopeEffectsRenderer.cs:681`）。
- 失败时的行为是**分级降级**：找不到 shader → 记一条日志 → 关闭对应功能，不崩。

### 6.9 【无 stub / 无硬断言】本次移植**没有**引入任何 `#if`、空实现占位或伪造 API

- 全部 30+ 处映射都落在真实存在的类型/成员上（第 5 节 72/72 EXISTS）。
- 唯一「降级为空操作」的是 6.1 那条 transpiler，且它是**原样保留的原版代码**，不是新写的 stub。

### 6.10 【防御性加固】`Newtonsoft.Json` 的 `NoInlining` 边界（解析成功时行为等价）

- **位置**：`Patches\PerScopeMeshSurgerySettings.cs`（389 → 505 行），文件内注释标题 "Json bridge"。
- **做了什么**：把**唯一两处** `JsonConvert` 调用移进 `DeserializeJson` / `SerializeJson` 两个
  `[MethodImpl(MethodImplOptions.NoInlining)]` 表达式体包装器，调用处用 try/catch + 异常过滤器（`when (IsJsonBackendFailure(...))`）包住；
  另加 `IsJsonBackendFailure`（只认程序集加载类异常）与 `OnJsonBackendUnavailable`（一条无条件 Warning + 会话内禁用 JSON 路径）。
- **完整的动机、逐条「行为等价」论证、以及自动化的 containment 守卫** 见 **2.6（5）**，此处不重复。
- **风险等级**：**无**（当解析成功时）。这是本次唯一一处**为防御而加、但不改变正常路径行为**的改动，
  其关键不变式已由核对脚本自动断言：
  `Newtonsoft.Json containment: 2 method(s) reference it, 0 of them lack NoInlining (expect 2 / 0)`。
- **为什么明知（2.6）的三条判据成立还要做**：后果不对称 —— 旧写法一旦解析失败会**每帧抛异常**
  （`MeshSurgeryManager` / `ReticleRenderer` 取值路径），恰好伪装成「移植失败 / 画面坏掉」，会污染实机诊断数据；
  把它降级成「一条警告 + 用内置默认值继续跑」的成本只有十几行，且现在还没开始实机测试，重建不产生额外成本。

## 10. ★ 新增功能：自适应切割区（从瞄具几何推导，替代手调常数）

### 10.1 为什么需要它

`custom_mesh_surgery_settings.json` 里 82 条**按瞄具**的切割参数，是原作者在 4.0.13 时期
针对当时的瞄具 prefab 手调的常数。4.1.5 的 prefab 换了之后，同一组数字对不同瞄具的
**贴合程度**就不再一致：

| ScopeKey | Plane1Radius | Plane2Radius@Pos | Plane3Radius@Pos | Plane4Radius@Pos | CutStartOffset / CutLength | NearPreserveDepth |
|---|---|---|---|---|---|---|
| `scope_30mm_sig_tango6t_1_6x24`（**坏**） | 0.02076 | 0.02145 @0.0810 | 0.13239 @0.4092 | 0.2 @1.0 | 0.040845 / 2.0 | 0.04333 |
| `scope_34mm_s&b_pm_ii_5_25x56`（**好**） | 0.02123 | 0.02145 @0.1514 | 0.10704 @0.2589 | 0.2 @1.0 | 0.040845 / 2.0 | 0.04601 |

逐字段对比这两条 JSON：切割几何上只差 `Plane1Radius / Plane2Position / Plane3Position /
Plane3Radius / NearPreserveDepth`（`Plane2Radius`、`Plane4*`、`Plane1OffsetMeters`、`CutStartOffset`、
`CutLength`、`ExpandSearchToWeaponRoot` 完全相同）；其余差异（`ReticleBaseSize`、
`MeshReticle*Scale`、`WeaponScale*`、`VisualRecoilCompensation`）与切割区无关。
两条配置在模组状态、镜片透明化、光学相机压制、命令缓冲、FOV 接管上**逐字段相同**，
差别只在这几个半径/位置/保留深度上。坏瞄具的表现是镜内看到「灰/黑 + 马赛克拉伸」的**镜筒内壁**——
即瞄具自身镜体没有被切割区删掉。结论：**不该继续手调常数，改成从几何量出来**。

### 10.2 新增配置（都在 `[Global Mesh Surgery settings]` 分类下）

| 键名 | 默认 | 说明 |
|---|---|---|
| `Auto derive cut region from scope geometry` | `true` | 总开关。**关 = 与改动前逐位一致** |
| `Auto derive margin` | `1.15` | 半径再乘这个系数（`R = min(max(R_geo,R_manual)*margin + extra, max radius)`） |
| `Auto derive extra radius meters` | `0.005` | 乘完再加的常数（米） |
| `Auto derive max radius meters` | `0.25` | 半径上限（米） |
| `Auto derive log derived profile` | `false` | 每次推导打**一行**日志；**独立于 `Debug logging`**，可单独打开 |

> 说明：任务书建议的 `[Mesh Surgery]` 分类在本工程里叫 `[Global Mesh Surgery settings]`
> （原版就没有名为 `Mesh Surgery` 的 section），为不打散相关旋钮，5 个新项放进这个既有分类。
> 这 5 项都是**全局**项，不参与按瞄具 JSON 覆盖（JSON 只覆盖几何参数本身）。

### 10.3 算法

入口：`MeshSurgeryManager.RebuildCutCacheForOptic`（**每次缓存重建算一次，绝不每帧**；
切割参数构建位置原本在 per-mesh 循环里，现已按「循环不变量」提到循环外，值不变）。
推导发生在 `RestoreOriginalMeshes(cache)` **之后**，所以量到的是**原始**网格的 bounds，
而不是上一轮被切过的网格。重建触发点：开镜（`ScopeLifecycle.cs:946`）、倍率切换（193）、
换弹结束恢复（366）、自由视角结束（`FreelookTracker.cs:175`）、持有武器背包变动（599-620）、
切割设置签名变化（85-90）。
注：`MeshSurgeryManager.RetryPendingCut` / `HasSuccessfulCut` 在**本移植版里没有任何调用方**
（`ScopeLifecycle.Tick` 里那句 "Tick() will retry" 注释是过时的），所以不存在「首帧 bounds 未就绪
→ 自动重试」这条路径；首帧 bounds 若异常，靠上面这些触发点重建才会重新推导。

```
轴      origin = TryGetPlane 给出的 planePoint（**已含 Plane1OffsetMeters 偏移**，即
                 真正传给 CutMeshFrustum 的那个中心点）
        dir    = 该 plane 的 normal（世界坐标单位向量）
        cutStart = -CutStartOffset      cutEnd = cutStart + CutLength
        （注意符号：CutMeshFrustum 的 IsInsideFrustum 把 t=0 放在 axial == -startOffset，
          所以这里用的 d 与切割器同一套带符号坐标；见 10.5 偏离说明 D1）
候选    LensTransparency.CollectHousingRenderers(os)（已排除镜片/准直发光体/空网格）
        —— 取不到时退化为「本次已收集的 targets 中位于瞄具子树内的那些」（见 D3）
单件    取 r.bounds（世界 AABB）的 8 个角：
          a  = dot(corner - origin, dir)            // 轴向坐标
          p  = |(corner - origin) - a*dir|          // 到轴的垂直距离
        a0=min(a)  a1=max(a)  rmax=max(p)
包络    d ∈ [cutStart, cutEnd] 上以 ≤10 mm 步长采样：
          R_geo(d) = max{ rmax : a0 - 5mm ≤ d ≤ a1 + 5mm }
        无任何 renderer 覆盖的采样点 → 取最近已知值（全都没有 → 0）
手调    R_manual(d) 用 MeshPlaneCutter.RadiusAtT4（**与切割器同一套分段线性插值**）
        四个平面：Plane1Radius@t=0、Plane2Radius@GetPlane2PositionNormalized(cutLen)、
        Plane3Radius@Plane3Position、Plane4Radius@Plane4Position
控制点  scopeEnd = max(a1)（clamp 到 [cutStart+0.02, cutEnd]）；span = scopeEnd - cutStart
        d1 = cutStart             d2 = cutStart+0.25*span
        d3 = cutStart+0.55*span   d4 = cutStart+1.00*span
        Plane*Position 一律回写成 (d - cutStart)/CutLength（clamp 到 0..1）
合成    R = min( max(R_geo, R_manual) * margin + extra, maxRadius )，再对每个控制半径取
        「手调曲线在该控制点所辖区间上的最大值」作**下限**（见 D2）
回填    NearRadius@d1、MidRadius@d2、Plane3Radius@d3、Plane4Radius@d4；
        StartOffset / CutLength / NearPreserveDepth **原样不动**
        → 照旧调用 MeshPlaneCutter.CutMeshFrustum（keepInside 等参数不变）
```

### 10.4 安全性质：**只增不减（max 语义）**

这是这个功能唯一重要的性质，必须写清楚：

1. `R(d) ≥ R_manual(d)` 对 `[cutStart, cutEnd]` 上**每一点**成立，而不是只在 4 个采样点上成立。
   （`R_geo` 与 `R_manual` 都按 **≤10 mm** 步长采样，理论上可能低估手调曲线在单个采样间隔内的
   峰值；量级是 `斜率 × 5 mm`，本工程典型斜率下 <1 mm，相对 `margin=1.15` 与 `extra=5 mm` 可忽略。）
2. 因此开启自适应后**不可能比今天切得更少**：任何「原本能被删掉的几何」现在仍然会被删掉。
3. `maxRadius` 这个上限**不能**把结果压到手调值以下——下限在钳位之后再生效（D2）。
4. AABB 八角的估法相对于「真正的旋转半径」只会**偏大**（球体最坏 √3 倍，长方体最坏 √2 倍），
   误差方向始终是「切得更多」，属于安全方向。
5. 任何异常 → **一条 Warning + 回退纯手调值**，不会抛进游戏循环，也不会因此不切割。

**代价**：它也可能删掉比今天更多的**枪身**几何（例如瞄具前方的导轨/护木/镜环）。
上面这两支镜子按手调曲线在 t=1 处半径本来就是 0.2 m，自适应该处给出 `0.2*1.15+0.005 = 0.235 m`，
属于「更狠 17%」的量级；如果实机发现删多了，先把 `Auto derive margin` 调回 1.0
（此时远场恰好等于手调值，因为下限接管）。

**更需要注意的是近场**（比远场更容易看出差别）：
- `Plane1Radius` 拿到的是「**实测几何 span 的前 25% 区间上** `max(R_geo, R_manual)` 的最大值」，
  所以它同时反映①镜体实测半径、②该区间内手调曲线的峰值，再乘 `margin` 加 `extra`。
- 82 条配置里有 **37 条** `Plane1Radius < 0.008`（两支 G36 Hensoldt 是 **0.001**，Progress PU 0.0054，
  一堆 TA31 ACOG 是 0.0077）——**这些近场半径本身就盖不住 30/34 mm 镜筒**，正好是本次要修的
  「镜筒内壁挡视线」的高危名单，自适应该会把它们抬到镜体实测半径量级（≈0.03–0.05 m，`margin` 后）。
  这属于**预期内的修复动作**；若某支镜子因此删掉过多（镜环/底座消失），按上面同一姿势回退。
- **切割目标是整枪**（`FindTargetMeshFilters` 从 `weapon` 根收，与本次改动无关、行为未变），
  所以近场半径变宽 = 沿枪管轴向把洞挖得更粗（含机匣/镜座区域）。日志里 `nearR` 与
  `regionCombinedMax[0]` 是唯一能提前看出来的量。

### 10.5 相对任务书算法的偏离（逐条说明理由，没有静默简化）

- **D1（符号/原点）**：任务书写 `cutStart = CutStartOffset`。但 `CutMeshFrustum` 的
  `IsInsideFrustum` 里 `cutStart = -_cStart`，t=0 位于**带符号坐标** `-StartOffset` 处；
  且几何测量的原点必须是**加了 `Plane1OffsetMeters` 之后**的那个 `planePoint`（切割器实际用的中心）。
  所以实现用 `cutStart = -StartOffset`、`origin = 加过偏移的 planePoint`。
  若照字面用 `+StartOffset`，测量窗与真实切割区会相差 `2*StartOffset`（本工程 81 mm），
  对「坏瞄具恰好是眼前那一段镜筒没被切」这个场景正好错开最关键的一段。
- **D2（区间最大值 + 钳位后兜底下限）**：任务书写「取 4 个控制点回填 R(d)」，并在最后做
  `min(..., maxRadius)`。这两件事**合起来会静默变弱**：本工程两支镜的 `CutLength = 2.0 m`，
  而量到的几何 span 只有 ~0.35 m，于是 `Plane4Position` 只到 `0.175`，
  切割器在最后一个控制点之后**保持末值**——照字面实现，t>0.175 的半径会从手调的 0.2 m
  掉到 `R(scopeEnd) ≈ 0.08 m`，即显著弱于今天。因此：
  (a) 每个区间的**两个**端点控制半径都 ≥ 该区间上 `max(R_geo, R_manual)` 的最大值
      （切割器在控制点之间是线性插值、末尾是常值，这个构造才能保证逐点 ≥ 手调曲线）；
  (b) 钳位之后再取 `max(..., 手调值)`，保证 `maxRadius` 永远不会让结果弱于手调。
  净效果只是「把 max 语义真正做实」，方向仍然是更狠。**代价**：`maxRadius` 因此不再是严格上限
  （日志里可能看到 `nearR > maxRadius`，那是兜底下限在起作用）。
- **D3（回退集合收窄到瞄具子树）**：任务书说取不到 housing 时退化为「本次已收集的 targets」。
  但 `FindTargetMeshFilters` 是从 **`weapon` 根**开始收的（`ExpandSearchToWeaponRoot` 默认 true），
  整枪 AABB 会把半径直接顶到 `maxRadius`，等于沿枪管轴钻一个 2×0.25 m 的洞——枪会缺一块。
  更糟的是 `CollectHousingRenderers` 对**准直瞄具**（`CollimatorSight` 下的 renderer）返回空列表，
  于是「恰好是红点/全息」会走这条最危险的路径（本移植刚修好的 EOTech HHS-1 就在其中）。
  故回退集合收窄为 `targets` 中**位于瞄具子树内**的 MeshFilter；瞄具子树内也没有 → 见 D4。
- **D4（无可用几何 → 返回纯手调）**：任务书写「无覆盖取 0」，而 `R = max(0, R_manual)`
  仍会被 `margin/extra` 放大成 `手调*1.15+0.005`。既然没有任何几何可量，这种「无依据的放大」
  没有收益，所以实现直接返回**未改动的手调档案**（等于今天的行为，不是更弱）。
  同一个规则也覆盖「有候选几何、但没有任何候选与切割窗口在轴向上重叠」的情况
  （`covered=0`，例如该 prefab 的轴向约定与预期不符）——同样返回纯手调并打一行日志，
  而不是拿一个零包络去放大手调值。
- **D5（采样步长上限）**：任务书写固定 0.01 m 步长。实现对 `CutLength` 很大时（JSON 里已有 2.0）
  会把采样数限制在 4096：步长取 `span/ceil(span/0.01)`（正常情况仍 ≤ 10 mm），
  仅在 span > 40.96 m 时才会粗于 10 mm——避免病态配置下的巨量分配。
- **D6（配置分类名）**：见 10.2 的说明（`[Global Mesh Surgery settings]` 而非 `[Mesh Surgery]`）。
- **D7（额外跳过的候选）**：任务书要求跳过 `null / !enabled / 无 mesh`。实现另外跳过
  `!gameObject.activeInHierarchy`（`CollectHousingRenderers` 本来就这么过滤；回退路径补上），
  以及 `mesh.vertexCount == 0`（空网格的 bounds 是退化的，会污染包络）。
- **D8（自查/复审后的三处加固，均为「不改方向、只改可诊断性与边界」）**：
  (1) **采样窗严格等于切割窗**：原先为保证 `Mathf.Clamp(scopeEnd, cutStart+0.02, cutEnd)` 的
      `min ≤ max` 会把 `cutEnd` 扩到 `cutStart+0.02`，导致 `CutLength < 0.02` 时采样窗比真实
      切割窗更长、四个 `Plane*Position` 被 `Clamp01` 挤到 1.0（`Plane3/4` 变成同一个死控制点）。
      现改为把**钳位下界**取成 `Min(cutStart+0.02, cutEnd)`、不再扩 `cutEnd`，采样范围与切割范围
      逐位一致，也不会出现 `scopeEnd > cutEnd` 的自相矛盾日志。
  (2) **所有回退路径都打一行**（`-> hand-tuned profile kept`）：`src=none`、`covered=0`、
      `axis-degenerate`、`cut-length-invalid`、`non-finite radii`。原先只有前两条有日志，
      「开了开关却没有任何行」无法区分「没跑」与「没量到」。
  (3) **日志的 `scope=` 诚实标注**：按瞄具 JSON 未命中时打印 `scope='<global>'`（此时手调值来自
      全局项），并新增 `optic='<os.name>'`；原先会回退成白名单 key 或对象名，诱导调参者去翻
      一行**并未生效**的 JSON 条目。
- 未偏离的其他点：候选来源、8 角 AABB 估法、5 mm 包络松弛、0.25/0.55/1.00 的控制点比例、
  `[cutStart+0.02, cutEnd]` 的 scopeEnd 钳位、`keepInside` 等其余实参保持不变、
  推导只在瞄具变化/缓存重建时发生、日志开关默认关且只打一行。

### 10.6 可观测性

打开 `Auto derive log derived profile` 后，每次推导恰好一行（`LogSource.LogInfo`，不受
`Debug logging` 影响）：

```
[MeshSurgery][Auto] scope='<json key 或 <global>>' optic='<os.name>' src=housing|opticTargets candidates=N
 nearR=.. midPos=.. midR=.. p3Pos=.. p3R=.. farPos=.. farR=..
 (geoR@cutStart(d=..)=.. geoR@mid(d=..)=.. geoR@p3(d=..)=.. geoR@far(d=..)=.. measured=[T,F,..]
  regionManualMax=[..] regionCombinedMax=[..] regionKnot=[..]
  manualNearR=.. cutStart=.. cutEnd=.. scopeEnd=.. cutLen=.. startOff=.. nearPreserve=.. step=..
  margin=.. extra=.. maxRadius=..)
```

- `scope=` **只在按瞄具 JSON 命中时**才是那行 `ScopeKey`；没有对应行时打印 `scope='<global>'`
  （此时手调值来自 `[Global Mesh Surgery settings]` 全局项，不是 JSON）——`optic=` 给出对象名，
  两者一起看才不会调错行。
- 所有 `d`（含 `cutStart`）都在**切割器自己的带符号坐标系**里：`t=0` 位于 `d = -CutStartOffset`，
  **不是** `d = 0`，所以 `geoR@cutStart(d=-0.0408)=...` 是正常值。
- `measured=[...]` 才表示「这个控制点位置真的量到几何了」；`geoR@*` 是**补洞之后**的包络，
  外推值看起来和量到的一样。
- `regionManualMax / regionCombinedMax / regionKnot` 是**区间**（不是单点）最大值，`regionKnot`
  是最终四个控制半径；`manualNearR` 与 `regionManualMax[0]` **本来就不相等**（后者是第一个区间上
  手调曲线的峰值，前者是 `t=0` 那一点的手调值）。
- `nearR > maxRadius` 是**合法**的：`maxRadius` 是上限，但钳位之后还有「不得弱于手调」的兜底下限
  （见 D2），兜底优先。
- 所有**回退路径**也各打一行（都以 `-> hand-tuned profile kept` 结尾，同受该开关控制）：
  `src=none candidates=0`（没量到任何几何）、`covered=0`（量到了但都不与切割窗重叠）、
  `axis-degenerate`、`cut-length-invalid`、`non-finite radii`。所以「开了日志却一行都没有」
  只可能是**还没发生重建**（见下一条），不会是「这条路径没日志」。
- **开关实时生效，但日志只在下一次重建时产生**：切开关本身不触发重建（它刻意不入设置签名），
  需要重新开镜 / 切一次倍率 / 换弹结束恢复等触发一次重建才会看到该瞄具的行。
- 推导会额外调用一次 `LensTransparency.CollectHousingRenderers`，因此 `Debug logging = true` 时
  每个镜体 renderer 的 `[LensTransparency] HousingMask +renderer: ...` 行会出现两次（纯日志噪音）。
- 是否「切了 0 个网格」不在这行里（它在 per-mesh 循环之前产生）；那件事看既有的
  `[MeshSurgery][DEBUG] RebuildCutCache finished with ZERO entries!` / `RebuildCutCache OK: N entries`。
- 首次推导失败会打一条**无条件 Warning**（不受任何开关控制，**每个进程只打一条**——
  `_autoDeriveFailureLogged` 不在换局/换枪时重置，与 `_jsonBackendUnavailable` 同一风格），文案形如
  `[MeshSurgery][Auto] Geometry derivation failed - ... Falling back to the hand-tuned per-scope cut profile for this rebuild.`。
- 每次切割的既有日志 `[MeshSurgery] Cut '<mesh>': N → M verts` 保持原样（随 `Debug logging`）。

## 12. 【已废案】视锥精确切割（View-frustum-exact cut）

> **本节所述功能已判定废案并从本仓库回滚 —— 代码中不存在对应的类、配置键与工具脚本。**
> 保留本节仅为记录失败原因，避免后来者重走同一条路。

曾尝试用一个通用公式从主相机视锥反推四个控制点半径，替代 §10 的最大包络推导：
`r(d) = d · tan(FOVv/2) · √(1 + aspect²) · margin`。

**失败原因：无法获取精确数值并且计算出正确值，导致负结果。**

技术实质：热键是在**已经开镜、网格切割已经生效**的时刻触发测量的，而测量读到的是插件自己上一次切割的产物（`*_CUT` 网格），
于是 `profile(n+1) = f(profile(n))` —— 闭环自反馈。同一瞄具、相机参数完全不变（`fovV=35.0000 aspect=1.6000`）连按四次，
P4 半径在 **0.0027 ~ 0.1996** 之间漂移 **70 倍**（`span` 0.2199 / 0.2202 / 0.0444 / 0.2990，候选数 2 / 2 / 1 / 3）。
附带恶化项：候选集按 `activeInHierarchy` 过滤 ⇒ 候选数随帧变化；搜索根含导轨底座 ⇒ 包络被非瞄具部件撑大。

曾提交一版测量纯化修复（改为解析回切割前原始网格、候选集与帧状态无关、日志打印被测量候选名与原始顶点数以自证），
静态验证 9/9 通过（含 IL 级证据与反向对照），**但未获实机验证即随本功能一并回滚**。

根本判断：**「挡住视线的几何」与「瞄具自身外壳」是同一块几何的两端** —— 这是取舍，不是可解方程。
与 §10 的判据一致：*切割结果对半径不敏感，约束在轴向窗口而非半径*。
