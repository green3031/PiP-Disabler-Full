## 一、热成像（T7）与瞄准镜的交互问题

这一类问题的共同症状是：**开启头盔热成像（T7，放下=开启）后，瞄具镜内全黑**；关掉热成像立刻恢复正常。它**只在部分场景/时序下出现**，且**切枪（重新实例化武器）通常能临时修好**。

### 1.1 靶场（射击场）首次进入 + 热成像开启 ⇒ 1 倍瞄具黑

- **触发**：在仓库里把头盔 T7 调到**放下（开启）** → **首次加载**射击场 → 开镜看 1 倍全息/红点 → **黑**。
- **绕过**：**切枪**（换一把枪再换回来）即恢复正常。
- **实机对照**：**真实战局（工厂）同一配置下是正常的** —— 这个问题主要表现为**靶场**特有。
- **用户决定**：**不修**（"靶场那个 bug 修不修无所谓了。不影响"）。

### 1.2 带着热成像**更换瞄具** ⇒ 新装上的瞄具黑

- **触发**：热成像开启状态下，在背包里把导轨上的瞄具换成另一支（红点 ⇄ 复合瞄具等）→ 开镜 → **新瞄具黑**。
- **绕过**：**切枪**。
- **用户决定**：**不修**（这是停止继续迭代的直接原因）。

### 1.3 开镜过程中 热成像 关→开 ⇒ 可能变黑

- **触发**：保持开镜，把 T7 关掉再开启 → 镜子变黑。
- **绕过**：切枪。

### 1.4 机制说明（便于理解，不代表已完全证实）

已实测到的关键事实：

1. 镜片着色器按 `_ThermalVisionOn` 二选一：`1` → 采样**热成像图**，`0` → 采样 **`_CamTex`**（画中画纹理）。
2. 本模组为了让「放大倍镜内看到热成像」，会**清空镜片的网格**并**压掉原版光学相机**（同时把全局 `_CamTex` 置为 `NULL`），使镜内画面变成**主相机**画面（因此继承热成像后处理）。
3. **原版** `ThermalVision.OnPreCull()` 每帧把全局 `_ThermalVisionOn` 写成 `1`（`OnPostRender()`/`OnDisable()`/`OnDestroy()` 写 0）。
4. ⇒ 只要**还有镜片面在绘制**、同时又**采不到有效画面源**，热成像开着时它就会渲染成黑；热成像关掉后全局变 0、改采 `_CamTex`，于是"看起来正常"。

**为什么只有 1 倍镜受害、放大倍镜没事**：放大倍镜的镜片**被本模组清空了**（不绘制 ⇒ 镜内=主相机画面）；而 **1 倍全息/红点（collimator）的镜片被模组有意保护、没有清空**（它同时承载准星点，见下），所以它仍在绘制。

**为什么"切枪"能修好**：切枪会让武器与瞄具**重新实例化**，模组对新的实例重新走一遍接管流程。

### 1.5 ⚠️ 一个必须知道的取舍：**准星点**与**全黑**是同一块几何的两端

1 倍 collimator 的**准星点**是由 `mode_*/linza_*` 这个渲染器（着色器 **`CW FX/Collimator`**）画出来的 —— 也就是**被保护的那一片镜片**。

- **清空它**：黑屏消失，**但准星点也没了**（实机验证过）；红点/全息没有点是不可用的。
- **保留它**：准星点正常，但上面 1.1–1.3 的黑屏就存在。

最终版**选择保留它**（即保点），因此接受 1.1–1.3 的黑屏，改用**切枪**绕过。

## 二、按瞄具个体问题（结案保留，不再修）

**这是取舍，不是可解方程**：挡住视线的那块几何本来就是瞄具自身外壳的一部分。「视线被挡」与「模型被删」是同一取舍的两端。

| 瞄具 | 现象 | 建议 |
|---|---|---|
| SIG TANGO6T 1-6x24 | 模型缺失 ＋ 黑边厚（**可用**） | 发布包内的 `custom_mesh_surgery_settings.json` 已含该镜修正值 |
| Monstrum Tactical Marksman 3×30（`scope_all_monstrum_marksman_3x30`） | 全黑 | **建议加入旁路**（见下） |
| TA02 4x32 | 放大过头 | — |
| Monstrum 2x32 | 画面比镜框小 | — |
| ADO P4 | 边缘空隙 | — |

**推荐旁路配置**（该镜在本模组下全黑，旁路后至少作为原版瞄具可用）：

```
Auto Bypass Name Contains = d-evo; scope_ags_npz_pag17_2,7x; monstrum_marksman_3x30
Scope Blacklist Names     = scope_all_monstrum_marksman_3x30
```

> 最省事的做法：给 `Scope Blacklist Toggle Entry Key` 绑一个键，**开镜状态下按它**即可把当前瞄具加入/移出黑名单。

## 三、已经试过、**失败**的修复路线（不要重走）

以下每一条都经过实机验证并被否定。记录下来，是为了让后来者不必重复付出同样的实测成本。

| 路线 | 结果 |
|---|---|
| **`T7ScopeHook` 逐材质钉零**（`BetterThermalNightVision` 里对瞄具材质强写 `_ThermalVisionOn = 0`） | **被受控实验证伪**。关掉它之后黑屏依旧，而且症状**随 T7 实时切换** —— 一次性写入、跟材质实例活到底的机制**物理上不可能**被"当场关掉 T7"撤销。文献里"同一段代码既是病因又是解药"的说法，是因为**两类瞄具需要的值正好相反**（放大倍镜需 0、1 倍镜需 1），而该代码对所有 MeshRenderer 一律写 0，**结构上不可能对两类都正确**。 |
| **视锥精确切割**（按 `r = d·tan(FOV/2)·margin` 反推切割半径，取代"最大包络"） | **废案**。热键在"已开镜、切割已生效"的时刻测量，读到的是**插件自己上一次的切割产物**，构成自反馈：同一瞄具连按四次，P4 半径在 0.0027~0.1996 之间漂移 **70 倍**。**无法获得稳定的"精确数值"** ⇒ 判定失败。 |
| **让 collimator 镜片也参与隐藏 + 每帧维持不变量** | **部分生效但引入新 bug**：黑屏确实消失，但**准星点也没了**（两者是同一块几何，见 §1.5）。 |
| **对"换镜后黑屏"的修复**（把"画面还活着就退让"改成"画面活着就把光学相机重新压下去"） | **实机判定为坏修复**：进战局时红点就是黑的。已回退。 |
| **F12 数值输入修复**（ConfigurationManager 的 50px 文本框改自绘滑块+宽输入框） | 静态验证通过，但因与其它实验同批打包、始终未获独立实机验证；结案时一并回退。 |

## 四、诊断工具（PiPDiag）自身的已知缺陷

这些缺陷在本次排查中**直接造成过两次错误结论**，记录下来：

1. **`lensParticipatesInImage` 曾不看 `Renderer.enabled` / `forceRenderingOff`** ⇒ 一个 `enabled=false`、根本不绘制的镜片照样被判"参与成像"，判词输出「典型镜内全黑」⇒ 误诊。（已修）
2. **判词是"条件句"而非观测**：`verdictThermalInScope` 只吃热成像事实、不含瞄准态/归属态，语义是"**若**这镜片在画面里，它就会黑"。把它当证据用就会错。
3. **瞄具解析可能解析到"别的枪上的瞄具"**（`SceneScan` 兜底不校验是否属于手持武器），而判词仍按"你正在看的镜"来写。而且它**恰好在被测模组正常工作时**才会走到这一级。
4. **字段陷阱**：`★LENS★` dump 里的 `active=` 是 `activeSelf`（不是 `activeInHierarchy`）；`optic.enabled` / `currentSightBoneIsOptic` / `mainCameraFov` **都不能**用来判断"玩家是否在开镜"（复合瞄具场景下会误判）。
5. **F9 在解析不到瞄具时会 dump 整把武器**（258 个节点、约 680 KB），而不是明确报错。
6. **把新 DLL 复制进 `plugins\` 不影响正在运行的进程** —— 必须重启游戏；否则你看到的是旧版本的行为（本次因此白跑过一轮）。

## 六、1.5.17：为什么把「自动推导切割区」默认关掉

### 6.1 起因

有玩家报告：**所有高倍镜开镜时都不显示枪身**。维护方本地无此问题。

### 6.2 根因：一个"全局"配置项没跟着发布包走

发布包只含 `plugins\PiP-Disabler\` 下的 7 个运行时文件；**`BepInEx\config\com.fiodor.pipdisabler.cfg` 是 BepInEx 首次运行时按代码默认值生成的，不在包内**。而两者刚好相反：

| 配置项 | 代码默认值（新装玩家拿到） | 维护方 cfg（实测） |
|---|---|---|
| `Auto derive cut region from scope geometry` | **`true`** | **`false`**（手动关的） |

⇒ **每个全新安装都会跑这个已被判定有害的算法**，而维护方因为早把它关掉，所以一直正常。

### 6.3 它为什么有害（三步，均已核对源码）

1. **只会切得更多** —— 合成式 `R = min(max(R_geo, R_manual) × 1.15 + 0.005, 0.25)`，
   手调 `Plane1Radius` 仅 **1.1 cm**，推导值取自瞄具外壳包围盒（约 4~5 cm）⇒ 半径被放宽约 4 倍。
   设置说明原文即：*"auto mode can only ever cut MORE than the hand-tuned profile, never less."*
2. **切割器删的是包络内部** —— `MeshSurgeryManager.cs` 传 `keepInside: false`，
   对应 `MeshPlaneCutter.cs` 的 `keepTri = !in0 && !in1 && !in2`。**半径放宽 ⇒ 删除范围变大。**
3. **切割区覆盖整把枪** —— `ExpandSearchToWeaponRoot` 默认 `true`（源码注释 `//Needs to be hardset`），
   且 `CutLength = 2` 米 ⇒ 这条沿枪管的切割区会一路吃到武器本体。

### 6.4 ⚠️ 不要混淆两个同名概念

排查中一度把两者并成一条，特此区分：

| | 机制 | 结局 |
|---|---|---|
| **视锥精确切割** | `半径(d) = d·tan(FOV/2) + 余量` | **§三表里的废案**（自反馈，P4 半径漂移 70 倍） |
| **自动推导切割区** | 「取全部壳体最大半径」包络，`max(推导, 手调)` | 是**那个废案想要取代的对象**，两个是对手，不是同一个 |

「自动推导切割区」未被称作废案，但同样是**已判定有害、已停用**的算法。

### 6.5 证据强度（诚实标注）

- ✅ **已验证**：默认值为 `true` 且未随包发布；算法只会放宽半径；切割器删包络内部；切割区覆盖整把枪。
- ✅ **已验证**：维护方 cfg 里该值为 `false`；`战局问题-分析记录.md` 另记有实测
  「`Plane1Radius×4` 让 Monstrum **镜身**消失」。
- ⚠️ **属推断**：由"镜身被删"顺延到"**枪身**被删"依赖 `ExpandSearchToWeaponRoot` 那条链，
  合理但**未经实机复现**。玩家原话为「不显示枪身」，也可能指镜身，或本就属原版行为
  （EFT 高倍镜开镜时不显示枪身）。
- ⚠️ **待观察**：若问题影响面是全体新装用户，理论上应有多人反馈，实际仅一例 ⇒ 不排除另有他因。

### 6.6 处置

不改算法本身（维护方已定版、不再迭代），只把**默认值翻正**，让新装用户拿到与作者已验证配置一致的状态。
老用户需手动关闭或删除 cfg（BepInEx 不覆盖既有值）。
